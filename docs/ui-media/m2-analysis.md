# วิเคราะห์สื่อ UI ภารกิจที่ 2

## ขอบเขตและลำดับที่เห็นจากภาพ

ตรวจภาพทั้งหมด 60 ไฟล์: `UI/ภารกิจที่ 2/` จำนวน 38 ไฟล์ และ `UI/ภารกิจที่ 2/example use flow/` จำนวน 22 ไฟล์ ภาพเลข 39–61 เป็น flow/storyboard ที่ทีมตั้งใจให้ดูตามลำดับ ส่วนภาพเลข 1–38 เป็นชุดกราฟิกและ mockup อ้างอิง

ลำดับการใช้งานที่อ่านได้จาก flow มีดังนี้

1. เปิดเกม/หน้าต้อนรับและเลือกวิธีเรียน: ดู, อ่าน, หรือจำลองสถานการณ์ (ภาพ 55)
2. Briefing ภารกิจที่ 2: โดมอธิบายสถานการณ์และแสดงแถบความคืบหน้า (ภาพ 56)
3. แผนที่ภารกิจ แสดงด่าน 1 เปิดอยู่และด่านถัดไปล็อกไว้ (ภาพ 57)
4. หน้าชื่อเกม/โลโก้ก่อนเริ่ม (ภาพ 58)
5. โหมดดู: โดมอธิบายเรื่องที่หน้าร้านและแสดงตัวอย่างชื่อเว็บ (ภาพ 50–52, 41–43)
6. โหมดดูต่อ: ตัวอย่างชื่อเว็บที่สลับลำดับ/ยังโหลดไม่สำเร็จ และตัวอย่างที่ถูกต้อง (ภาพ 44–49)
7. โหมดลงมือทำ: สอนลากชิ้นส่วน `www`, ชื่อร้าน, `.com` ลงช่อง (ภาพ 45–47 และ mockup ภาพ 23–38)
8. เกมตรวจคำตอบ: จัดชิ้นส่วนให้เป็นชื่อเว็บ แล้วตอบคำถามยืนยันความเข้าใจ (ภาพ 19–22, 31–38)
9. โหมดอ่าน: อ่านเรื่องราว/บทสนทนาแบบการ์ดหรือ chat reader แล้วตอบคำถาม (ภาพ 25–30)
10. สรุปผลและไปภารกิจถัดไป (มีใน mockup ภาพ 14–16 และภาพ 48)

ภาพ 39–40 และ 53–54 เป็น storyboard รวม ใช้ยืนยันลำดับภาพและจังหวะ ไม่ใช่หน้าจอ runtime แยกต่างหาก ภาพ 59–61 เป็น contact sheet/storyboard รวมอีกชุด จึงไม่ควรนำไปแสดงเป็นภาพเดียวในแอป

## ภาพ mockup เต็มจอ กับ asset ที่นำกลับมาใช้ได้

### Mockup เต็มจอหรือภาพอ้างอิงหน้าจอ

ภาพ 12–38 เป็นหน้าจอแนวตั้งของเกมหลายสถานะ: แผนที่, briefing, tutorial, เกมต่อชิ้นส่วน, คำถาม, chat และผลลัพธ์ ภาพ 41–52 เป็น visual shot แนวนอนของเรื่องร้านขนม ภาพ 55–58 เป็นหน้าจอ flow หลัก ภาพ 39–40, 53–54, 59–61 เป็น storyboard/contact sheet

ภาพเหล่านี้มีข้อความ ปุ่ม และคำตอบฝังอยู่ในภาพ จึงใช้ได้แค่เป็น reference สำหรับ layout/สี/จังหวะ ไม่ควรใช้เป็น background ใน runtime เพราะจะทำให้ข้อความซ้ำ อ่านไม่ได้ และแก้เนื้อหา/การเข้าถึงไม่ได้

### Reusable asset ที่เห็นในภาพชุด 1–11

- ภาพ 1: แผ่นตัวอย่าง layout/กรอบการ์ดและดาว — reference ไม่ใช่ asset เดี่ยว
- ภาพ 2: ไอคอนควบคุม (ย้อนกลับ, ตรวจ, ผิด, hint, home, pause, replay, sound) — ใช้เป็น reference; ระบบมี icon component อยู่แล้ว
- ภาพ 3: ปุ่มสีเขียว/ส้ม/ฟ้า/ม่วง และสถานะปุ่ม — ใช้เป็น reference; ปุ่ม runtime ต้องเป็น HTML
- ภาพ 4: กล่องชิ้นส่วนโดเมน/ไอคอนบริการ/โทรศัพท์ — มีตัวอักษรในภาพ จึงไม่ควรใช้ตรง ๆ เป็น asset runtime
- ภาพ 5: ชิ้นส่วน `www`, SLD, Subdomain, TLD และกรอบ — เป็น reference สำหรับ card/slot ที่ควร render ด้วย HTML
- ภาพ 6: ช่องวางชิ้นส่วนพร้อมป้าย TLD/SLD/Subdomain — reference สำหรับ drop target
- ภาพ 7: badge ตัวเลข 1–4 — นำแนวคิดไปทำด้วย HTML/CSS ได้
- ภาพ 8: ป้ายส่วนประกอบโดเมนแบบแถบสี — reference สำหรับ status chip
- ภาพ 9–10: ชุดชิ้นส่วนคำตอบ/ชิ้นหลอก — ข้อความฝังในภาพ ใช้เป็น reference เท่านั้น
- ภาพ 11: ตัวละครโดม — เป็นภาพบนพื้นขาว ไม่มี alpha ที่ส่งมาด้วย; ระบบมี `public/dome/mascot/*.webp` แบบโปร่งใสอยู่แล้ว จึงใช้ของระบบต่อไป

## ความต่างจาก implementation ปัจจุบัน

1. ภาพทีมใช้แถบหัวสีน้ำตาลเข้ม ตัวอักษรเหลือง ปุ่มส้ม/เขียว และพื้นร้านขนม/เมืองสีสว่าง; ปัจจุบัน m2 ใช้พื้น garage โทนม่วงและ header ขาว
2. ภาพทีมใช้กรอบ/ปุ่มแบบเกม 2D มีขอบเข้มและเงาชัด; ปัจจุบันใช้ glass card และ clay shadow ที่เรียบกว่า
3. ภาพทีมมี mascot ตัวม่วงขนาดใหญ่เป็นผู้พูดในหลายจอ; ปัจจุบันใช้ DomeAvatar ของระบบ ซึ่งเป็น asset โปร่งใสที่ semantic/accessibility ดีกว่า แต่ขนาดและตำแหน่งยังไม่ตรงทุก mockup
4. โหมดดูของปัจจุบันแสดงวิดีโอจริงหรือ `LearnScenePanel` ที่เป็น SVG schematic; flow ทีมแสดง visual shot แนวนอนและข้อความบนการ์ดด้านล่าง
5. เกมปัจจุบันยังคงการจัดชิ้นส่วนด้วย HTML/interaction จริง แต่ภาพทีมมี tutorial, timer, progress และ card แบบเกมมากกว่า
6. โหมดอ่านของปัจจุบันเป็น chat reader ที่เลื่อนทีละข้อความ; mockup ทีมแบ่งเป็นบทสนทนา/กล่องข้อมูลและมี quick check สีม่วง
7. ปัจจุบันมี stage bar, back/menu และ footer dock แบบแอป ซึ่งไม่ปรากฏชัดใน mockupทีม แต่จำเป็นต่อการใช้งานจริงและการทำต่อจากจุดเดิม

## ความต่างด้านเนื้อหาและคำตอบ

`content/learn-paths.json` m2 ปัจจุบันใช้แกนหลัก 3 ส่วน: ซ้ายคือ `www`/Subdomain, กลางคือชื่อหลัก/SLD, ขวาคือ `.com`/TLD และย้ำการอ่านจากขวาไปซ้าย ตัวอย่างใน watch/read คือ `www.kanombanyai.com`, `parts.forcespeed.com` และ quick check ให้เลือก `.com` เป็น TLD ซึ่งตรงกับคำตอบใน `content/learn-paths-answers.json` และการตัดสินใจใน `state.md` ว่า Padlet แบบ 3 ส่วนเป็น canonical

ภาพทีมใช้ตัวอย่างเพิ่ม/ต่างออกไป เช่น `booking.kanombanyai.com`, `shop.kanombanyai.com`, `shop.kanombanyai.shop`, การสลับ `com.kanombanyai.shop` และชิ้นหลอก `playflower`, `order`, `co`, `.th` รวมถึง wording แบบ `Visual`, `Text`, `Simulator` และ tutorial หลายขั้น ตัวอย่างเหล่านี้ยังไม่ได้อยู่ใน answer key ปัจจุบันทั้งหมด โดยเฉพาะ `.shop`, `booking` และโจทย์ชิ้นหลอก จึงยังไม่เปลี่ยน content หรือ server grading ในรอบนี้

การตอบที่มีอยู่ใน server ยังเป็นคำตอบที่ไม่เปิดเผยใน public JSON และการ personalize m2 ต่อ student ยังใช้ต่อเหมือนเดิม ห้ามย้ายเฉลยจาก `learn-paths-answers.json` ไป public asset

## คำถามที่ยังเปิดอยู่

1. จะให้ flow ใหม่ของทีมเป็น canonical แทน Padlet 3 ส่วนปัจจุบันหรือไม่ หรือเป็น visual/tutorial layer ของ learn path เดิม
2. ต้องเพิ่มตัวอย่าง `booking`, `shop`, `.shop`, `playflower`, `co`, `.th` และคำตอบ/เกณฑ์ใหม่เข้า server grading หรือไม่
3. ภาพแนวนอนชุด 41–52 ต้องใช้เป็นฉากจริงราย scene หรือเป็น storyboard/reference เท่านั้น ถ้าใช้จริงควรมีไฟล์ต้นฉบับที่ไม่มีหัวข้อ/คำอธิบายฝังในภาพ
4. ต้องทำหน้าต้อนรับ/แผนที่/โลโก้ของภาพ 55–58 ให้ตรงใน route อื่นด้วยหรือจำกัดเฉพาะ learn path m2
5. mascot ในภาพทีมเป็นตัวละครคนละชุดกับ DomeAvatar ปัจจุบันหรือไม่ และมีไฟล์ PNG/WebP โปร่งใสต้นฉบับให้ใช้หรือไม่
6. ค่าความก้าวหน้าในภาพ (เช่น 3/5, timer, ด่าน 1–4) เป็นเพียงภาพประกอบหรือเป็น requirement ของ state และ teacher panel

## สิ่งที่ทำได้โดยไม่เดา

รอบ implementation ควรปรับเฉพาะ visual shell ของ m2 ให้เป็นพื้นร้านขนม/โทนอุ่น, header และ control ที่มี contrast ผ่าน, ขอบ/ปุ่ม/การ์ดตาม reference และคง text/button เป็น HTML โดยไม่เปลี่ยนลำดับ step, server grading, answer key, learn-path event หรือ teacher panel จนกว่าจะได้คำตอบเรื่อง content ด้านบน

## 1. ระบบนี้คืออะไร พูดแบบภาษาคน

**เว็บแอปหนึ่งตัว ที่เปิดพร้อมกันได้ 3 บทบาท**

- **นักเรียน** เปิดบนมือถือ เล่นเกมตั้งชื่อโดเมนให้ร้านของตัวเอง
- **ครู** เปิดบนโน้ตบุ๊ก เห็นทั้งห้องกำลังทำอะไรอยู่แบบสด ๆ ควบคุมจังหวะคาบได้
- **ระบบ** อยู่ตรงกลาง คอยจำว่าใครอ่อนเรื่องไหน แล้วปรับระดับตัวช่วยให้แต่ละคน

**ไม่ใช่เกมที่แจกไปให้เล่นเอง** — เป็นเครื่องมือที่ครูใช้ระหว่างสอน เกมเป็นเพียงส่วนที่นักเรียนมองเห็น

## 2. ครูได้อะไร ไล่ตามนาทีในคาบ

| ช่วงเวลา | ครูเคยทำอย่างไร | มีระบบนี้แล้วทำอย่างไร |
|---|---|---|
| ก่อนคาบ | เตรียมสไลด์ชุดเดิมทุกปี | กดสร้างห้อง ได้รหัส 6 ตัวและ QR ฉายขึ้นจอ ตั้งเวลาแต่ละช่วงไว้ล่วงหน้า |
| นาทีที่ 0–5 | เช็กชื่อ รอเด็กพร้อม | เด็กสแกน QR เข้าเอง ครูเห็นตัวเลขขึ้นเรื่อย ๆ ว่าเข้ามาแล้วกี่คน |
| หลังแบบทดสอบก่อนเรียน | ไม่รู้ว่าห้องนี้รู้อะไรมาแล้ว ต้องเดา | **เห็นทันทีว่าข้อไหนทั้งห้องตอบผิด** รู้ว่าต้องเน้นสอนตรงไหนในอีก 20 นาทีข้างหน้า |
| นาทีที่ 5–25 (สอน) | สอนตามสไลด์ | ภารกิจถูกล็อก เด็กไม่แอบเล่น และ **ยกงานของเด็กในห้องขึ้นมาเป็นตัวอย่างสด** |
| นาทีที่ 28–48 (ทำภารกิจ) | เดินดูทีละโต๊ะ 30 คน ดูไม่ทัน | **แผงห้องเรียนสด** จุดเขียว เหลือง แดง เห็นในหน้าจอเดียวว่าใครติด เดินตรงไปหาคนแดงได้เลย |
| | ไม่รู้ว่าใครขอความช่วยเหลือ | เด็กกดปุ่มขอความช่วยเหลือ จุดของเขากะพริบบนแผงครู |
| | จัดกลุ่มสอนเสริมด้วยความรู้สึก | ระบบบอกว่า "5 คนนี้ติดเรื่องนามสกุลโดเมนเหมือนกัน" เรียกมารวมกลุ่มสอนซ้ำครั้งเดียวจบ |
| นาทีที่ 48–55 (ส่งงาน) | ตรวจงาน 30 ชิ้นทีหลัง | AI ประเมินเบื้องต้นให้ก่อน ครูกดยืนยันหรือแก้คะแนน **ครูตัดสินใจเสมอ ไม่ใช่ AI** |
| หลังคาบ | จบคาบก็จบ | รายงานรายคนและรายห้อง เทียบก่อน–หลังเรียน คาบหน้าเริ่มจากโปรไฟล์ล่าสุด |

**ประโยคเดียวสำหรับตอนนำเสนอ**
ครูมองเห็นสิ่งที่มองไม่เห็นตอนเดินดูทีละโต๊ะ และตัดสินใจได้ทันในคาบ ไม่ใช่รู้ตอนตรวจงานเสร็จสัปดาห์หน้า

## 3. สองบทบาท สองระบบเข้าสู่ระบบ ไม่เหมือนกัน

### 3.1 ครู — บัญชีจริง

| รายการ | รายละเอียด |
|---|---|
| วิธีเข้า | อีเมล + รหัสผ่าน หรือเข้าด้วยบัญชี Google |
| ใช้อะไรทำ | Supabase Auth (มีให้ในตัว ไม่ต้องเขียนระบบเอง) |
| ทำไมต้องมีบัญชีจริง | เป็นเจ้าของข้อมูลทั้งห้อง ใช้ข้ามเทอม ต้องกู้บัญชีได้ และต้องมีสิทธิ์ยืนยันคะแนน |

สิทธิ์ของครู
- สร้างและปิดห้องเรียน
- ปลดล็อกสถานีให้ทั้งห้อง ขยายเวลา
- ดูแผงห้องเรียนสด
- ยืนยันหรือแก้คะแนนที่ AI เสนอมา
- ดาวน์โหลดรายงาน
- เตะผู้ใช้ที่ไม่ควรอยู่ในห้องออก

### 3.2 นักเรียน — ไม่มีบัญชี

**ขั้นตอนเข้าเกม**

1. สแกน QR ที่ครูฉายขึ้นจอ
2. ใส่รหัสห้อง 6 ตัว (ถ้าสแกน QR รหัสจะเติมให้อัตโนมัติ)
3. พิมพ์ชื่อเล่น
4. ตั้งรหัส 4 หลัก
5. เข้าเกม

**เหตุผลที่ไม่ให้สมัครสมาชิก**

| เหตุผล | รายละเอียด |
|---|---|
| เวลา | นักเรียน 30 คนสมัครสมาชิกใน 5 นาทีเป็นไปไม่ได้ ยืนยันอีเมลไม่ทันแน่นอน |
| กฎหมาย (PDPA) | ไม่เก็บชื่อจริง อีเมล หรือเบอร์โทรของเด็ก เก็บแค่ชื่อเล่นกับคำตอบ อธิบายต่อกรรมการได้ชัด |
| ความเป็นจริง | นักเรียน ปวช.1 ไม่ได้มีอีเมลที่ใช้งานจริงทุกคน |

## 4. รหัส 4 หลักมีไว้ทำอะไรกันแน่

**ไม่ใช่รหัสผ่านหลัก**

สิ่งที่ใช้ระบุตัวตนจริง ๆ คือ **session token ที่เซิร์ฟเวอร์ออกให้ เก็บใน httpOnly cookie** ผูกกับเครื่องนั้น
รหัส 4 หลักใช้เฉพาะ 2 กรณี
1. นักเรียนย้ายไปใช้อีกเครื่อง
2. เผลอล้างข้อมูลเบราว์เซอร์แล้วต้องเข้าใหม่

**เหตุผล** รหัส 4 หลักมีความเป็นไปได้แค่ 10,000 แบบ ถ้าใช้เป็นรหัสผ่านหลัก เพื่อนเดาเข้าบัญชีกันได้ไม่ยาก
เก็บลงฐานข้อมูลต้อง **hash เสมอ ห้ามเก็บเป็นตัวเลขตรง ๆ**

## 5. ปัญหาที่ต้องกันไว้ตั้งแต่ออกแบบ

| ปัญหา | วิธีแก้ |
|---|---|
| ชื่อเล่นซ้ำกันในห้องเดียว | ตรวจตอนพิมพ์แบบเรียลไทม์ ถ้าซ้ำให้เปลี่ยนหรือเติมเลขต่อท้ายอัตโนมัติ |
| เพื่อนเดารหัส 4 หลักเข้าบัญชีกัน | จำกัดการลองผิดไม่เกิน 5 ครั้งต่อ 10 นาทีต่อชื่อเล่น และแผงครูขึ้นธงเตือนถ้าชื่อเดียวกันเข้าจาก 2 เครื่องพร้อมกัน |
| ห้องคอมพิวเตอร์ใช้เครื่องร่วมกัน | มีปุ่มออกจากระบบชัดเจน และ session หมดอายุอัตโนมัติเมื่อครูกดปิดคาบ |
| นักเรียนเข้าสายตอนภารกิจถูกล็อก | รหัสห้องใช้ได้จนกว่าครูจะกดปิด เข้ามาแล้วเห็นหน้ารอพร้อมสรุปสั้นว่าครูสอนอะไรไปแล้ว |
| คนนอกเดารหัสห้องเข้ามา | รหัส 6 ตัวสุ่ม ใช้ได้เฉพาะช่วงที่ครูเปิดห้อง และครูเห็นรายชื่อทุกคนที่เข้ามา เตะออกได้ |
| เด็กเล่นต่อที่บ้าน | ครูกำหนดวันหมดอายุของห้องได้ หลังจากนั้นเข้าไม่ได้อีก |

## 6. กฎความปลอดภัยที่ห้ามละเมิด

> **ทุกครั้งที่บันทึกข้อมูล เซิร์ฟเวอร์ต้องอ้างอิงจาก session cookie เท่านั้น**
> **ห้ามเชื่อค่า student id ที่ส่งมาจากเบราว์เซอร์เด็ดขาด**

ถ้าเขียน API แบบ `POST /api/progress { studentId, score }` แล้วเอา `studentId` จาก body ไปใช้ตรง ๆ นักเรียนที่รู้วิธีจะแก้คะแนนตัวเองหรือของเพื่อนได้ทันที
รูปแบบที่ถูกคือ `POST /api/progress { score }` แล้วเซิร์ฟเวอร์อ่านว่าใครส่งมาจาก cookie เอง

มาตรการเสริม
- เปิด Row Level Security ของ Supabase ทุกตาราง ให้แต่ละแถวอ่านและเขียนได้เฉพาะเจ้าของกับครูเจ้าของห้อง
- key ของ Supabase ฝั่งเซิร์ฟเวอร์ (service role) **ห้ามหลุดไปฝั่งเบราว์เซอร์** ใช้เฉพาะใน API route
- จำกัดจำนวนครั้งที่เรียก AI ต่อคนต่อคาบ กันทั้งการเล่นนอกเรื่องและค่าใช้จ่ายบานปลาย

## 7. โครงตารางฐานข้อมูลเบื้องต้น

```
teachers          id, email, name, created_at
classrooms        id, teacher_id, room_code(6), status, opens_at, closes_at
students          id, classroom_id, nickname, pin_hash, device_token, created_at
                  UNIQUE (classroom_id, nickname)
profiles          student_id, business_name, business_type, confidence,
                  pre_test_score, post_test_score, scaffold_level(1-3)
progress          student_id, station, status, attempts, hints_used,
                  started_at, completed_at
submissions       student_id, domain_name, tld, reason_text,
                  ai_scores(jsonb), teacher_confirmed_scores(jsonb),
                  needs_review(bool)
events            student_id, type, payload(jsonb), created_at   -- log สำหรับทำรายงาน
```

ตาราง `events` คือสิ่งที่ทำให้เขียนรายงานตอนท้ายได้ — บันทึกทุกการกระทำไว้ก่อน ค่อยเอามาสรุปทีหลัง

## 8. สิ่งที่ต้องทำก่อนเขียนโค้ด

| ลำดับ | งาน |
|:---:|---|
| 1 | สร้างโปรเจกต์ Supabase + เปิด Auth แบบอีเมล และ Google |
| 2 | สร้างตารางตามโครงข้อ 7 + เปิด Row Level Security ทุกตาราง |
| 3 | เขียน API route สำหรับเข้าห้อง (`/api/join`) ที่ออก session cookie |
| 4 | หน้าเข้าห้องของนักเรียน + หน้าเข้าสู่ระบบของครู |
| 5 | ทดสอบด้วยคน 5 คนพร้อมกันก่อน แล้วค่อยขยายเป็น 30 |
